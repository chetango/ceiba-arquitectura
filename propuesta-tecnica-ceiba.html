El Problema

Los países de América Latina enfrentan un volumen masivo de hurto vehicular. Las cámaras de monitoreo existen, pero no están conectadas con las bases de datos policiales — cada país opera en un silo.

Problema técnico central: conectar hardware heterogéneo en campo, microservicios en la nube y bases de datos policiales de múltiples países — con cero tolerancia a pérdida de eventos.

La Solución: 3 Capas

📷 Capa Edge — Dispositivos en Calle
Worker Service .NET en cada cámara. Patrón store-and-forward con SQLite — ningún evento se pierde aunque caiga la conectividad o la energía. Comunicación vía MQTT con mTLS.
☁️ Capa Cloud — Microservicios en Kubernetes
5 microservicios ASP.NET Core / Worker Service: Ingesta, Detección, Consulta, Notificaciones y Analytics. Desacoplados por RabbitMQ. Desplegados en Kubernetes — cloud-agnostic.
🔗 Capa de Integración — Heterogeneidad por País
Patrón Adapter por país para normalizar bases de datos de vehículos hurtados. Keycloak como broker de identidades que federa LDAP, AD, SOAP y REST sin tocar el sistema central.

🔌 Mecanismo de Acceso al Hardware

  • El componente de reconocimiento expone un socket TCP local en localhost:7000
  • El Recolector hace polling cada 500 ms — vía TcpClient en .NET
  • Protocolo: frames delimitados por longitud (4 bytes length + JSON payload)
  • ¿Por qué no HTTP? Overhead innecesario en loopback con 1 GB RAM
  • Si el hardware expone named pipe (Linux): mismo Worker, distinto transport

📦 Store-and-Forward

  • Siempre guarda primero en SQLite
  • Sincroniza cuando hay conexión GSM
  • Cero pérdida de eventos mientras el dispositivo está encendido
  • Batería de respaldo: 1h de captura garantizada ante falla de energía

🔐 Seguridad mTLS

  • Cada cámara: certificado X.509 único
  • Autenticación mutua con el broker
  • Revocación remota desde la nube

🔁 Idempotencia

  • Cada evento tiene event_id UUID
  • INSERT ... ON CONFLICT DO NOTHING
  • Duplicados descartados silenciosamente

🆕 Enrolamiento de Dispositivos Nuevos

  • Bootstrap cert: certificado temporal emitido en fábrica, corta vida
  • El Worker lo usa para hacer la primera solicitud al CA interno
  • cert-manager emite el certificado X.509 definitivo del dispositivo
  • Bootstrap queda revocado — válido para una sola solicitud
  • Renovación automática antes del vencimiento: cero intervención manual

Arquitectura Interna — Clean Architecture + CQRS

Estructura interna de cada microservicio .NET: separación por capas, CQRS para desacoplar lecturas de escrituras, MediatR como bus de comandos.

📐 Clean Architecture

  • Domain: entidades y reglas sin dependencias externas
  • Application: casos de uso con MediatR. Un handler = un caso de uso
  • Infrastructure: EF Core, MassTransit, MinIO — detalles de implementación
  • API/Worker: entry point; traduce MQTT/HTTP/RabbitMQ a Commands

⚡ CQRS con MediatR

  • IngestEventCommand: guarda evento + foto + publica en RabbitMQ (Outbox)
  • DetectStolenVehicleCommand: compara placa, publica alerta
  • GetPlateHistoryQuery: historial paginado con URLs de fotos
  • Validación con FluentValidation via pipeline behavior

🗃️ Repository + EF Core

  • Repositorios genéricos por agregado, Unit of Work para transacciones
  • Índices compuestos (matricula, fecha_evento) en PostgreSQL
  • INSERT ... ON CONFLICT DO NOTHING para idempotencia

Estrategia de Pruebas

Pirámide de pruebas para garantizar calidad en cada capa — desde el handler MediatR hasta el flujo completo con infraestructura real.

🔬 Unit Tests

  • xUnit + NSubstitute
  • Handlers MediatR en aislamiento
  • Domain entities y reglas de negocio
  • Sin base de datos — mocks de repositorios
  • Cobertura objetivo: >80% en Application + Domain

🔗 Integration Tests

  • Testcontainers .NET
  • PostgreSQL real en Docker
  • RabbitMQ real en Docker
  • Prueba el flujo completo Command → DB
  • Verifica idempotencia con event_id duplicado

📜 Contract Tests

  • Pact (.NET)
  • Contratos entre microservicios via RabbitMQ
  • Consumer-Driven: el consumidor define el contrato
  • Evita romper consumers al cambiar publishers

🏋️ Load Tests

  • k6
  • Simula 2,500 dispositivos enviando eventos
  • Valida SLA de <30s de latencia end-to-end
  • Detecta cuellos de botella antes de producción
GitHub Actions: Unit Tests en cada PR · Integration Tests en merge a main · Load Tests en release candidates

Patrón Adapter
Un Worker .NET por país. Si una BD cambia su protocolo, solo se modifica ese adaptador — el sistema central no se toca.
Keycloak como broker
El sistema habla solo con Keycloak. Keycloak habla con LDAP, AD, SOAP, REST de cada país. JWT estándar para todos.
Sincronización: Pull + Push
Pull (por defecto): polling cada 15 min para países con BDs sin notificaciones.
Push (preferido): si el país ofrece webhook o CDC, el adaptador se suscribe y actualiza en segundos — sin cambiar el sistema central.

Decisiones Clave de Diseño

MQTT sobre HTTP para dispositivos IoT

Conexión persistente, bajo consumo de ancho de banda, QoS integrado. HTTP requiere una conexión por evento — inviable con 1 GB RAM y GSM intermitente.

→ MQTTnet (.NET) · Mosquitto → EMQX a escala

Patrón Adapter por país (no ETL centralizado)

Aísla la complejidad de cada integración. Cambios en una BD externa solo afectan su adaptador. Nuevos países = nuevo Worker Service, sin tocar el core.

→ Un Worker .NET por país · Formato estándar hacia PostgreSQL

Keycloak como broker de identidades

Open source, cloud-agnostic, soporta nativamente LDAP/AD/SOAP/REST. El sistema nunca toca los sistemas de autenticación de cada país directamente.

→ Descartados: Azure AD B2C (lock-in), Auth0 (costo), IdentityServer (desarrollo manual)

Dead Letter Queue + monitoreo activo

Mensajes corruptos no bloquean el flujo principal. 5 reintentos con backoff exponencial vía MassTransit, luego DLQ. Grafana alerta si DLQ > 0.

→ UseMessageRetry · Prometheus plugin RabbitMQ · Alert Grafana

Outbox Pattern — consistencia transaccional

El Servicio de Ingesta hace INSERT en PostgreSQL y publica en RabbitMQ en la misma transacción lógica. Sin Outbox, un fallo entre ambas operaciones genera inconsistencia.

→ MassTransit Outbox integrado · tabla outbox en PostgreSQL · proceso relay automático

Apache Superset para analytics

Conecta directo a PostgreSQL sin ETL adicional. Soporte nativo para mapas de calor geoespaciales. Open source, sin licencia. Camino de evolución: agregar TimescaleDB cuando escale — sin cambiar esquema ni queries.

→ Descartado: Power BI (licencia + lock-in Microsoft)

React + TypeScript en lugar de Blazor WASM

React es el estándar del mercado para frontends de alta interactividad. Blazor WASM tiene bundle inicial de 10+ MB y ecosistema reducido. React se integra con el cliente JS de SignalR y React Leaflet nativamente.

→ Vite · React 18 · TypeScript · React Leaflet · @microsoft/signalr

Roadmap de Implementación

Tres fases incrementales — cada entrega es un sistema funcional utilizable por la policía.

Fase 1 · ~4 meses

MVP — Detección y Alerta

  • 2 países piloto · 500 dispositivos
  • Flujo completo: cámara → detección → alerta
  • Worker Service edge con store-and-forward
  • Adaptadores para 2 BDs de vehículos robados
  • Frontend: mapa + historial + alertas en tiempo real
  • Keycloak con LDAP/AD de ambos países
✅ Policía detecta y recibe alerta en <30 seg
Fase 2 · ~3 meses

Escala + Analytics

  • 5 países · 2.500 dispositivos
  • Apache Superset — dashboards analíticos
  • Mapas de calor: zonas de hurto, rutas de escape
  • EMQX si el volumen de dispositivos lo requiere
  • Gestión remota de dispositivos (Eclipse Hawkbit)
  • Observabilidad completa: ELK + Grafana + OTel
✅ Análisis de tendencias operativo para 5 países
Fase 3 · continua

Expansión Global

  • 50+ países · decenas de miles de dispositivos
  • TimescaleDB para time-series a escala masiva
  • DR activo-activo multi-región Kubernetes
  • Machine Learning: predicción de zonas de riesgo
  • API pública para integración con terceros
✅ Plataforma global de seguridad vehicular
